WHITE NOON · seguridad · documento local (no se publica)

Dónde vive la llave
y por qué nadie la ve.

El chatbot del portfolio habla con Azure OpenAI. Eso necesita una API key — la cosa más peligrosa de filtrar. Esta guía te enseña, con un diagrama vivo y comprobaciones que puedes correr tú mismo, exactamente dónde está esa llave, por qué tu navegador (y cualquier atacante mirando el código) nunca la ve, y cómo verificarlo.

La idea en una frase. La llave nunca está en el código ni en lo que se descarga el navegador. Vive cifrada en los servidores de Cloudflare y solo se inyecta, en memoria, dentro de una pequeña función de servidor en el instante de hablar con Azure. El navegador del visitante solo ve /api/ask — jamás la llave.

El salto del medio (Cloudflare → Azure) ocurre servidor a servidor. Ese tramo nunca toca el navegador, así que la llave nunca viaja a través de él hacia el visitante. La respuesta que vuelve al navegador es solo texto + enlaces del propio sitio.

2 · ¿Cómo es esto posible? Las tres reglas

Regla 1 — La llave es una variable de entorno, no una línea de código

En el código del repo, la función pide la llave así — fíjate en que no hay ninguna llave escrita, solo el nombre de una variable que Cloudflare rellena en ejecución:

// functions/api/ask.js (esto SÍ está en git — y es seguro) headers: { 'api-key': env.AZURE_OPENAI_API_KEY } // ← un hueco, no un valor

El valor real lo pones una sola vez en el panel de Cloudflare (paso 4). Cloudflare lo guarda cifrado y lo inyecta en env cuando la función se ejecuta. Git nunca lo ve; el build nunca lo ve.

Regla 2 — Hay una frontera entre "navegador" y "servidor"

Todo lo que vive en src/ se compila y se descarga al navegador — ahí jamás puede ir un secreto. La carpeta functions/ es distinta: Cloudflare la ejecuta en su servidor, nunca se envía al navegador. La llave solo se toca dentro de functions/.

Por eso el chatbot llama a /api/ask y no a Azure directamente. Si el navegador llamara a Azure, tendría que llevar la llave consigo → filtrada al instante. El /api/ask intermedio es justamente el muro que mantiene la llave del lado seguro.

Regla 3 — El secreto local también está fuera de git

Para probar en tu portátil con wrangler pages dev usas un fichero .dev.vars. Está en .gitignore, así que nunca se sube. En el repo solo hay .dev.vars.example con placeholders, jamás valores reales.

3 · Compruébalo tú mismo (no te fíes, verifica)

Corre estos comandos en la raíz del proyecto. Cada uno demuestra una garantía. Resultado esperado: que tu llave NO aparezca por ningún lado salvo en Cloudflare.

Construye el sitio y busca tu llave (o su prefijo) en TODO lo que se sube al navegador. Debe salir 0 coincidencias:

npm run build findstr /S /I /M "TU-PREFIJO-DE-LLAVE" dist\* :: Windows grep -rI "TU-PREFIJO-DE-LLAVE" dist/ :: macOS/Linux

También que functions/ no acabe en dist/ (Cloudflare la ejecuta aparte, no la empaqueta): dist/ no contiene api/ask.js como JS del navegador.

Comprueba que ningún fichero rastreado por git contiene la llave, y que .dev.vars está ignorado:

git grep -I "TU-PREFIJO-DE-LLAVE" :: debe imprimir NADA git check-ignore .dev.vars :: debe imprimir .dev.vars git ls-files | findstr ".dev.vars" :: solo .dev.vars.example, nunca .dev.vars

Con el sitio abierto, en DevTools → pestaña Network: pregunta algo al chat. Verás una petición a /api/ask (tu dominio) con tu pregunta en el cuerpo y sin api-key. NO verás ninguna llamada del navegador a *.openai.azure.com — ese salto es servidor-a-servidor.

En DevTools → Sources: busca (Ctrl+Shift+F) tu prefijo de llave en todos los recursos cargados → 0 resultados.

4 · Cómo se ponen las llaves (lo haces tú, una vez)

No puedo (ni debo) hacer este paso por ti: requiere tu cuenta de Cloudflare. Y es justo así como debe ser — el secreto solo lo conoces tú y Cloudflare.

Producción — panel de Cloudflare

  1. Cloudflare Dashboard → Workers & Pages → tu proyecto → Settings → Variables and secrets.
  2. Añade, marcando cada una como Secret (encrypt), estas 4 — los nombres exactos, tus valores reales:
    AZURE_OPENAI_ENDPOINT = https://TU-RECURSO.openai.azure.com (tu endpoint real) AZURE_OPENAI_API_KEY = (tu key — márcala SECRET) AZURE_OPENAI_DEPLOYMENT = gpt-5.4-mini AZURE_OPENAI_API_VERSION = 2024-12-01-preview

    Los valores reales (endpoint y key) solo los escribes aquí, en Cloudflare — nunca en un fichero del repo. Por eso este documento usa placeholders.

  3. Re-despliega (push a main o "Retry deployment"). Listo: el chat encuentra su voz.

Alternativa por terminal (wrangler)

npx wrangler pages secret put AZURE_OPENAI_API_KEY # te pide el valor de forma interactiva — nunca queda en el historial ni en un fichero

Local (para probar el chat en tu portátil)

copy .dev.vars.example .dev.vars :: y pon tus valores reales en .dev.vars (ya ignorado por git) npx wrangler pages dev -- npm run preview

6 · Si algo va mal

El chat dice "el asistente no está conectado"

La función devolvió 503 unconfigured: falta alguna de las 4 variables en Cloudflare, o el deployment no existe. Revisa el paso 4. El sitio sigue perfecto — solo el chat espera su voz.

¿Y si alguien me roba la llave igualmente?

Con esta arquitectura tendría que entrar en tu cuenta de Cloudflare o de Azure (ambas con su propio login/2FA) — no le sirve de nada mirar el código ni la red. Si sospechas: en Azure, regenera la key (Keys → Regenerate) y actualiza solo Cloudflare. La vieja muere al instante.

¿La pregunta del visitante es privada?

La pregunta viaja a Azure (tercero) para ser respondida — como cualquier asistente. No guardamos historial en servidor; el contexto se queda en la pestaña del visitante. El colofón del sitio ya divulga el uso de servicios externos.

WHITE NOON · esta guía es local y no contiene secretos · ábrela cuando quieras, compártela sin miedo · el chatbot responde con grounding del propio sitio y cita sus fuentes (precisión = solo afirma lo que el sitio puede probar).
